# 设计调研：别人怎么组织「任务、agent、额度、审批」（2026-11-03）

用途：044（界面）和 045（号池 + 能力档案）都从这页出发，不再从零拍脑袋。只记查到的事实和由此得出的取舍；查不到的写「没查到」。

## 一、看了谁、各自的骨架

| 产品 | 核心对象 | 怎么派活 | 怎么看进度 / 审 | 额度怎么呈现 |
|---|---|---|---|---|
| **Grok Bot**（SpaceXAI，托管） | 有名字的 Bot（角色、长期偏好、自己的对话）；一台共享云电脑，每个 Bot 一块屏；Skill（可复用流程，含审批边界）；Routine（定时 / 事件）；群聊 2–6 个 Bot | 对 Bot 说一句话；配置也用说的，不填表 | Bot 之间按角色分工、互相等依赖；缺连接时在对话里给「一键连接」；密码 / 验证码由人接手 | 每周上限；**用完 Bot 会卡在半路**（官方建议升级套餐）；文中没写额度表盘 |
| **Vibe Kanban**（开源） | 项目 → Issue（可有子 Issue）→ **Workspace**（一次 agent 运行，一个 Issue 可开多个并行比较）→ 每个仓库一个 worktree | 建 Issue，再开 Workspace，选 agent / 模型 / 计划模式 | 看板 + 右侧面板实时日志；Workspace 视图看 diff、预览应用；合并或开 PR | 没查到 |
| **Codex 应用** | 项目 → 线程（一件事一个线程），多个 agent 并行 | 每个任务开一个线程 | diff 优先的审阅；一键打开终端 / 编辑器 | 没查到 |
| **Devin / Cursor 后台 agent / Claude Code Routines / OpenHands** | 会话（session），各自一台云机或容器 | Slack、网页、接口、GitHub Issue | 完整回放或屏幕录像；完成后自动开 PR | 只有「并发上限」「超额计费」，都没有好的表盘 |
| **amux**（自托管看板） | 每个 agent 一个 tmux 会话 + worktree | 看板 | 实时终端、日志 | **到额度上限后自动续跑**、卡住会标出来、按 agent 记成本 |

## 二、借什么

1. **一件事 = 一个对象，一次运行 = 它下面的一条记录**（Vibe Kanban 的 Issue / Workspace，Codex 的线程）。我们现在是一个任务只有一条状态，重试会覆盖前一次。改成：任务下面挂多次运行（哪个执行者、哪个账号、花了多少、结局），可以并排比较。
2. **说一句话派活，不填表**（Grok Bot、Codex）。044 原型的顶部输入框就是这条。
3. **执行者有「人设」**（Grok Bot 的 Bot）：名字、擅长什么、长期偏好、手上的活。就是 045 的能力档案，在剧组页上用卡片呈现。
4. **到额度上限自动续上，卡住要标出来**（amux）。Grok Bot 用完额度就卡在半路，是反例。我们要做的是到上限 → 记下重置时间 → 换下一个账号槽或排到重置后，页面上看得到「在等 15:45 重置」。
5. **过程可回看**（Devin、OpenHands 的回放）。我们不录屏，用时间线：读了哪些网页、写了哪些文件、跑了哪些命令。
6. **Skill 和 Routine**（Grok Bot）。把一次成功的任务存成模板（含审批边界），定时任务复用它。这条排在 045 之后。

## 三、不借什么

- **共享云电脑、托管**：我们的卖点是跑在用户自己的电脑上、用自己的账号。
- **让 AI 批 AI 的自动审批**（Grok Bot 的 Auto Review）：决策记录里早定了，审批只由人点。039 的「只改文档自动过」是规则，不是模型判断，保留。
- **Bot 群聊互相派活**：会让一个人看不清谁在干什么。我们只有一个大脑派活，执行者之间不对话。
- **重型看板当首页**：看板适合几十个任务；个人一天几件到十几件，四列流就够。

## 四、对象模型（推广「项目 → 任务 → 执行者」）

六种对象，各有一张卡、一个详情，彼此能点过去：

```
项目 ─┬─ 任务 ─┬─ 运行（第 1 次、第 2 次…）─┬─ 用了哪个执行者
     │       │                            ├─ 用了哪个账号槽（花了多少额度）
     │       │                            └─ 过程时间线 / 结果 / 改动
     │       └─ 审批（属于某次运行）
     └─ 项目备忘
执行者 ─┬─ 能力档案（测评打底 + 自己的战绩）
       └─ 账号槽（每个槽：额度、窗口、重置时间、过期日）
```

页面上的关联：
- 从账号槽能看到「这周花在哪些任务上」。
- 从任务能看到「用了谁、哪个账号、花了多少」。
- 从项目能看到「在跑什么、谁擅长这个项目」。

## 五、能力档案：先用权威测评打底

查到的事实（全部来自聚合站，**没有一条是基准方独立复跑的**，所以只能当先验）：

- **SWE-bench Verified**（BenchLM，2026-10-29）：Claude Opus 5 96%，GPT-5.3 Codex 85%，DeepSeek V4 Pro 80.6%，DeepSeek V4 Flash 79%，Qwen3.7 Max 80.4%，Kimi K2.6 80.2%，GLM-5 77.8%。116 行里 110 行是厂商自报。前几名差距在 1 分以内，没有意义。
- **Terminal-Bench 2.0**（benchmarklist 从 vals.ai 导入，2026-07-28 采样）：GPT 5.5 73.2%，Claude Opus 4.8 70.0%，Kimi K2.6 57.3%，DeepSeek V4 Pro 56.2%，GLM 5.1 53.9%，Qwen 3.7 Max 59.2%。各页之间互相矛盾（同一页的说明和表格对不上）。
- **外壳（harness）影响和模型一样大**：同一个模型，厂商自己的外壳比标准化外壳可以高 10–30 分；同一组任务换 Claude Code、Codex、Pi 三种外壳，结果也不同。

由此定的规则：
1. 档案按「执行者 = 外壳 + 模型」记，不按模型名记：反代池（Claude Code + 百炼 DeepSeek）和 dsh（dsh + DeepSeek）是两个档案。
2. 测评只给三档先验：强、中、弱，分别对应「改代码」「终端 / 运维」两个维度。不给小数点，差距在 3 分以内的算同档。每条记来源和日期。
3. 自己的战绩每多 1 单，先验的权重就降一点：5 单以后战绩和先验各占一半，20 单以后先验只占两成。
4. 先验每季度刷新一次，刷新本身是一张需求单，不自动抓。
5. 大脑看到的是「强 / 中 / 弱 + 自己的战绩一行」，不是一堆分数。

## 六、账号槽（号池）：怎么真的用起来

- **订阅账号（Claude Pro / Max、ChatGPT）**：
  - 一个账号一个独立的登录目录（`CLAUDE_CONFIG_DIR`）。执行器现在已经给 Claude Code 单设了一个，扩成多个就行。
  - 官方命令行照常登录、照常用，工具不读、不搬凭证。
- **怎么知道额度还剩多少**：Claude Code 的状态栏脚本能拿到 `rate_limits.five_hour.used_percentage`、`seven_day.used_percentage` 和 `resets_at`（订阅用户才有，要等第一次请求之后）。执行器给每个槽配一个只写本地文件的状态栏脚本，就能按槽读到真实窗口。
- **到上限怎么认**：输出里出现「You've hit your session / weekly limit · resets …」这类话，就把这个槽标成「到 X 前不可用」。下一单换槽；这一单按 017 的后端切换逻辑换槽重跑。
- **API key 和代金券**：照 007 的顺序，先花快过期的，再花订阅窗口，最后花真钱。
- **只在本机**：工作台只存每个槽的名字、额度和重置时间，不存任何凭证。
- **风险提醒**：一个人开多个订阅账号，有的厂商条款不允许，没有核实。界面上写一句提醒，用不用由用户定。
