# 接一个新项目

工作台已经装好、能跑任务了，现在想让 AI 去改**第二个仓库**。按顺序做，一步一验。

一次只接一个。第一个项目跑通之前别接第二个，否则出问题分不清是谁的。

---

## 0. 先想清楚：这个仓库适合让 AI 改吗

| 适合 | 不适合 |
|---|---|
| 有 git、能本地跑、测试命令明确 | 没有版本管理、只能线上改 |
| 改错了能 `git checkout` 回来 | 一动就影响真实用户（生产库、支付） |
| 依赖能本地装 | 依赖只能在特定机器/内网装 |

不适合的仓库不是不能接，是**别让它自动跑**：把这个执行者的「能不能被自动领取」关掉，只能你点「开始」。

---

## 1. 在工作台里接入

### 1.1 仓库放哪

执行器要能直接读到它。建议所有仓库放在同一个父目录下，例如：

```
C:/code/my-app          ← 新项目
C:/code/ai-workbench    ← 工作台自己
C:/code/wb-worktrees    ← 执行器给任务开的临时分支，自动创建
```

### 1.2 加一行项目

编辑 `~/.ai-workbench-runner.json` 的 `projects`：

```json
{
  "projects": {
    "ai-workbench": "C:/code/ai-workbench",
    "my-app": "C:/code/my-app"
  },
  "worktreeRoot": "C:/code/wb-worktrees"
}
```

**测试核对（可选，默认开）**：AI 交活后，执行器会自己把项目的测试再跑一遍，和它说的对照，结果写在点头卡上。
项目里有 `package.json` 且有 `test` 脚本时，自动用 `npm test`，不用配。别的项目在执行器配置里写：

```json
{
  "tests": { "my-app": "pytest -q", "docs-site": "" },
  "verifyMinutes": 10
}
```

写空字符串就是这个项目不核对；`"verify": false` 整个关掉。命令只能是普通的一行（不能带 `;` `|` `&&` 引号这些）。
AI 这次改了 `package.json` 里的 `scripts` 时，执行器不会替它跑，点头卡上会写明要你看一眼。沙箱里的活在沙箱里跑。

`my-app` 这个名字**就是任务里「项目」字段要填的值**，两边必须一致。

也可以重跑安装脚本，它会保留已有内容只补新的：

```bash
npm run setup -- --yes --project my-app=C:/code/my-app --backend deepseek --key-file ~/.wb-key
```

### 1.3 `worktreeRoot` 是什么

执行器不会在你的工作目录里直接改代码。它用 `git worktree` 在 `worktreeRoot` 下开一个临时分支（`wb/T-<任务号>`），干完留给你审批；你批准了才合并回 main。

所以：

- `worktreeRoot` 要和工作台仓库**在同一个盘**（跨盘会很慢，某些系统上还会失败）；
- 它会自己建目录，不用你手动创建；
- 任务失败后临时分支会留着，可以手动删。

### 1.4 检查仓库里有没有 `.claude/settings*.json`

有的话执行器会**拒绝**这个项目：那个文件能让 agent 自己改权限规则，等于把门锁交给它。

```bash
ls .claude/
```

有就删掉（或者改名），再把要保留的规则写进工作台的「设置 › 安全 › 规则」。

### 1.5 用只读任务试第一次

别一上来就让它改代码。新建一个任务：

- 标题：`读一遍 README，用三句话说这个项目做什么`
- 执行者：随便一个在线的
- 项目：`my-app`

点「开始」，看它能不能领到、能不能读到文件、会不会停下来问。**这一步只验证链路，不验证能力。**

失败了看哪里：

| 现象 | 看这里 |
|---|---|
| 一直排队 | 执行器在线吗？项目名对不对？ |
| 领到了但马上失败 | 任务详情底部的执行器日志 |
| 说找不到项目 | 配置里的 `projects` 名字和任务里的不一致 |
| 说被拒绝 | 就是 1.4 那个 `.claude/settings.json` |

## 2. 要不要为这个项目调整分类和规则

大部分项目不用改。出现下面几种情况就要加：

| 这个项目有… | 加一条规则 |
|---|---|
| 部署脚本（`deploy.sh`、`docker compose up`） | 工具名 `Bash`，输入 `deploy\|compose up`，风险 **高** |
| 真实数据文件 | 工具名 `Edit\|Write`，输入 `data/`，风险 **高** |
| 生成物（`dist/`、`*.min.js`） | 不用拦，但要在项目的 `CLAUDE.md` 里写「不要提交生成物」 |
| 生产配置 | 工具名 `Edit\|Write`，输入 `\.env\.prod\|config/prod`，风险 **高** |

分类（dev / doc / content）决定哪个执行者能领。新项目如果只是写文档，把任务的分类改成 `doc`，别占用 dev 的执行者。

---

## 3. 谁来做计划：用决策端

工作台不负责想「做什么」，它只负责**派活、审批、记账**。想的部分交给决策端（一个能读仓库、能写需求单的模型会话）。

```
你 ──说需求──▶ 决策端 ──写需求单──▶ 仓库 docs/specs/
                                        │
                                   你（或 Issue）派单
                                        ▼
                                   工作台 ──▶ 执行器（coding）干活
                                        │
                                   回报写回需求单末尾
                                        ▼
                                   决策端审查 ──▶ 通过 / 打回
```

**开一个新项目的流程**（其实就是把上面那条线跑第一遍）：

1. 你回答五个问题：
   - 做什么（一句话）？
   - 给谁用（自己 / 家人 / 客户）？
   - 技术和部署有什么约束（必须 Node？必须能离线？跑在哪台机器）？
   - 什么叫做完（三条可验证的标准）？
   - 预算（能用多少 token / 多少钱，超过就停）？
2. 决策端产出四样东西：
   - 项目说明（写进仓库 `README.md`）；
   - `CLAUDE.md`（硬约束、目录结构、验证命令、哪些事必须停下来问人）；
   - 第一批 3–5 张需求单（`docs/specs/001-…md`），每张都小到能一次做完；
   - `docs/specs/README.md` 里的状态表。
3. 你审一遍需求单，觉得对，就说「开始」。
4. 之后每张单跑一轮：执行器做完 → 回报写进需求单末尾 → 决策端审 → 下一张。

模板都在 `docs/templates/new-project/`：

| 文件 | 复制到新项目的哪里 |
|---|---|
| `CLAUDE.md` | 仓库根目录 |
| `specs-README.md` | `docs/specs/README.md` |
| `DECISION-HANDOFF.md` | `docs/specs/DECISION-HANDOFF.md` |
| `000-template.md` | `docs/specs/000-template.md`（之后每张单从它复制） |

复制完把里面标着「填」的地方补上。**留空的项比写错的项危险**：决策端会以为那项不用管。

---

## 4. 让决策端每天也看这个项目

决策端早上有一次自动审查（8:23）。新项目要进它的视野，二选一：

- **改现有任务**：在那个定时任务的说明里加一句「也看 `用户名/my-app` 的 `docs/specs/`」；
- **新建任务**：给这个项目单独开一个定时任务，时间和现有那个错开十分钟，免得两个同时跑。

只改定时任务，不要给工作台加新的调度——工作台不负责叫醒决策端。

---

## 5. 接完检查一遍

- [ ] `node scripts/runner.mjs --check` 里多了一行「项目 my-app ✓」
- [ ] 工作台里建一个只读任务，能跑完
- [ ] 任务详情里「后端」显示的是你以为的那个
- [ ] 改动确实出现在 `wb/T-<号>` 分支上，不是直接改的 main
- [ ] 合并、推送两条审批都出现过
- [ ] 如果这个项目有部署脚本，规则已经加上，且试过一次会被拦
